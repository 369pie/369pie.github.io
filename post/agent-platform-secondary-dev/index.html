Agent 二次开发不是改 Prompt：OpenClaw / Hermes 工程化清单

2026年9月28日
| 技术

很多人把「Agent 二次开发」理解成换模型、加几个 Tool、写更长的 System Prompt。这在 Demo 阶段够用，但一旦要卖给真实用户（尤其是非开发者），失败点几乎总是工程问题：状态不可预测、升级不可回滚、出错不可定位。

在 OpenClaw、Hermes 一类可扩展 Agent 框架上做产品化时，我习惯把交付物拆成四层，而不是一层 Prompt：

  1. 能力层：工具、插件、MCP 连接——明确输入输出 schema 与超时。
  2. 策略层：规划/反思是否启用、最大步数、人工确认点（human-in-the-loop）。
  3. 运行层：进程隔离、凭据注入、网络 egress 白名单。
  4. 体验层：安装包、便携形态、一键更新与故障自检。

边界比功能重要

二次开发最容易膨胀的是「工具列表」。每多一个工具，组合爆炸就多一点，模型误调用的概率就高一点。工程上的做法是：

  • 每个工具必须有 idempotent 语义说明：重复调用是否安全。
  • 对「写操作」默认加确认或草稿态，而不是直接落库。
  • 把高危工具（文件删除、转账、发信）放进单独 Capability Profile，默认不启用。

这和微服务里的「最小权限」是同一逻辑：Agent 不是更聪明的 cron，而是带自然语言前端的自动化系统，权限模型不能省。

状态机，而不是聊天记录

生产级 Agent 需要可恢复的运行状态。仅依赖「把历史消息塞回上下文」会在长任务里失控：成本飙升、关键约束被挤出窗口、用户看不到进度。

更稳妥的模式是显式状态机，例如：idle → planning → executing → awaiting_user → failed → done。每次状态迁移写事件日志（谁触发、哪一步、用了哪个工具、耗时多少）。这样你可以：

  • 在 UI 上展示「卡在哪一步」；
  • 支持从 failed 带上下文重试，而不是让用户重讲一遍；
  • 做 A/B：同一任务不同策略层配置，对比成功率。

配置与发布：像发服务一样发 Agent

便携 U 盘形态、桌面安装包、云端 SaaS，本质都是配置分发问题。建议把以下内容版本化（Git 或配置中心均可）：

  • 模型路由表（主模型 / 备用模型 / 本地小模型）；
  • 工具清单与默认参数；
  • Prompt 模板（按 locale、按场景拆分，禁止一个巨型 Prompt 包打天下）；
  • Feature flags（例如是否开启深度搜索）。

发布流水线至少包含：静态检查（schema 校验）→ 回归用例（固定输入期望工具调用序列）→ 灰度（按设备或用户百分比）。没有回归用例的 Agent 升级，和没有单测的核心服务一样危险。

可观测：把「它又在瞎编」变成可量化事件

最少要采集三类指标：

  • 任务级：成功率、平均步数、用户打断率；
  • 工具级：调用次数、失败原因分布、P95 延迟；
  • 模型级：Token 用量、缓存命中、拒答/安全拦截次数。

二次开发的价值，最终体现在：同样的大模型，你的封装让任务成功率更高、成本更低、升级更可控。OpenClaw / Hermes 提供了起点，但产品化清单必须自己补齐——否则用户记住的只有「不稳定」。
