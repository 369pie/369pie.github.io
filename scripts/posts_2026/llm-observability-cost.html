做过统一监控平台的人会形成一种直觉：任何系统一旦上生产，不可观测就等于不可运营。大模型应用把这条规律放大了——同样的 HTTP 200，背后可能是 3 次重试、2 万次 Token、一次工具超时换来的「看起来对了」。

指标栈：别只盯 QPS

在传统微服务监控里，我们习惯 RED/USE。映射到 LLM 应用，我建议至少扩展为：

维度看什么为什么
请求成功率、P95 延迟、用户放弃率体验是否可用
模型输入/输出 Token、模型路由、拒答率成本与合规
工具调用拓扑、失败类型、重试次数定位「胡调工具」
会话轮次、上下文截断次数、摘要触发解释账单飙升

在 Klook 做流式监控时，我们强调「一条 trace 贯穿网关、服务、消息队列」。LLM 场景同样需要 trace_id 贯穿用户请求 → Agent 步进 → 每次 completion → 工具副作用，否则只能看到「今天贵了」，看不到「哪条产品路径贵了」。

成本：把 Token 当成 CPU 秒

财务视角要把 Token 纳入容量规划：

  • 按功能拆 cost per successful task，而不是按模型拆均价；
  • 对缓存命中、提示词压缩、小模型兜底分别记账；
  • 设预算告警：单用户、单租户、单实验组日上限。

很多团队翻车，是因为只监控「调用次数」，没监控「成功任务成本」。Agent 多步推理会让后者呈非线性增长。

SLO：用业务语言约束模型行为

示例 SLO（需按产品调整）：

  • 95% 的客服意图在 8 秒内给出可执行答案；
  • 工具写操作 100% 带审计日志；
  • 幻觉敏感场景（医疗、法律）必须命中检索增强，否则拒答。

SLO 的意义是把「模型感觉变笨了」翻译成可报警的阈值，并绑定降级策略：换小模型、缩短上下文、关闭高风险工具。

日志与隐私

全量存 prompt 在调试期很方便，上线后要做分级：默认存 hash + 结构化特征，抽样存原文，PII 脱敏。公开博客与社区文档里也不应出现真实用户信息——这与传统日志合规一致，只是 LLM 更容易「把隐私写进上下文」。

可观测性投入不会让用户直接点赞，但会在第一个「账单异常」或「口碑事故」时决定你是手忙脚乱，还是十分钟内定位到某次工具 配置发布。
